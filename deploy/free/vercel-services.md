# Vercel Services: Next.js и Django в одном проекте

Это основной бесплатный профиль для небольшого учебного стенда: сайт и API публикуются одним Vercel-проектом и открываются по одному адресу. Services находится в Beta и доступен на всех планах. База — Neon Free, ИИ — Cloudflare Workers AI Free, письма — защищённый SMTP существующей почты или Brevo HTTPS. Установка Docker не нужна.

Файлы подготовлены; успешная локальная проверка не означает, что облачный стенд уже опубликован.

## 1. Подготовить сервисы

- В Neon создай новую базу на Free рядом с Frankfurt и сохрани pooled PostgreSQL URL с `sslmode=require`. SQLite в Vercel не сохраняет данные между запусками.
- В Cloudflare открой Workers AI на Free, получи Account ID и API token с разрешением Workers AI. Нужны только разрешённые текстовая модель и генератор из шаблона; платных запасных моделей нет.
- Для почты выбери один из двух транспортов ниже. Без реального проверочного письма вход не считается готовым.

### Почта: SMTP или Brevo

**SMTP существующей почты.** Можно использовать аккаунт команды в Gmail, Яндекс Почте или почтовой системе вуза, если выбранный сервис разрешает SMTP для этого аккаунта. Возьми hostname, логин, разрешённого отправителя и пароль приложения из настроек провайдера. Обычный пароль аккаунта может не подходить; OAuth-only аккаунту потребуется другой способ настройки.

В Production укажи `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, `EMAIL_HOST`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` и `DEFAULT_FROM_EMAIL`. Поддерживаются только два сочетания:

| Подключение | EMAIL_PORT | EMAIL_USE_SSL | EMAIL_USE_TLS |
| --- | --- | --- | --- |
| TLS с начала соединения | 465 | true | false |
| STARTTLS | 587 | false | true |

Для SMTP ключ Brevo не нужен. Console/file/locmem backend, незашифрованное соединение и одновременное включение SSL/STARTTLS в production-профиле отклоняются. [Vercel не блокирует исходящий SMTP, кроме порта 25](https://vercel.com/kb/guide/serverless-functions-and-smtp), но доступность выбранного сервера, handshake, авторизацию и доставку нужно проверить из опубликованной Python-функции. Такая проверка ещё не выполнена; реальные SMTP-данные пока не подключены.

**Brevo HTTPS.** Существующий backend `tasks.email_backends.BrevoEmailBackend` сохранён: для него нужны `BREVO_API_KEY`, подтверждённый `DEFAULT_FROM_EMAIL` и доступ к transactional emails. SMTP-поля ему не требуются. Может понадобиться подтверждённый домен команды/вуза и активация отправки.

При заполнении профиля Brevo нужны страна и почтовый адрес организации; сервис предупреждает, что адрес может отображаться в письмах. В проверенной 3 ноября 2026 форме поиск `Russia` и `Russian Federation` не дал результата. Это препятствие регистрации, а не подтверждение общего запрета сервиса. Указывай действительные согласованные сведения; если заполнить профиль нельзя, используй SMTP выбранной почты.

Оба варианта заданы в [шаблоне окружения](vercel-services.env.example); включи только один блок и используй разрешённого выбранным провайдером отправителя.

Cloudflare получает сообщения и ограниченную часть данных доступных пользователю проектов. Пароли и служебные токены не выбираются, но произвольный текст описаний и комментариев может содержать внесённые пользователями данные.

## 2. Создать проект в Vercel

1. Выбери Hobby и импортируй репозиторий с актуальной веткой. **Root Directory — корень репозитория (`.`), Framework — Services**, конфигурация — корневой `vercel.json`.
2. Если Vercel GitHub App требует разрешения организации `261-327`, потребуется её владелец. Если прямой импорт запрещён на Hobby или доступ пока не согласован, используй личный fork с той же веткой. Покупать Pro для этого профиля не нужно.
3. Не задавай общий Build Command: у Django и Next.js отдельные команды внутри `services`. Node.js — 24; Python закреплён как 3.13 в `backend/.python-version`.
4. В настройках окружения включи **Enable access to System Environment Variables**. Для первой сборки `FRONTEND_URL` можно не задавать: Vercel передаст стабильный Production domain через `VERCEL_PROJECT_PRODUCTION_URL`, доступный при сборке и работе сайта. Для собственного домена можно позже явно указать точный HTTPS-адрес в `FRONTEND_URL`.
5. В Project Settings → Environment Variables добавь значения из [vercel-services.env.example](vercel-services.env.example) **только для Production**. В Preview не копируй рабочую базу, почту и ключи ИИ.
6. Production Branch должна содержать эту конфигурацию. Выполни Production deployment / Redeploy после сохранения окружения.

Ссылки восстановления пароля используют явный `FRONTEND_URL` или стабильный Production domain из системного окружения. Уникальный адрес отдельной сборки `VERCEL_URL` не становится основным адресом; заголовки запросов для этого не используются. Если стабильный адрес недоступен, сборка остановится до миграций.

В Services-профиле не используется ручная переменная `DJANGO_API_URL`: Vercel внедряет её в frontend из приватного binding к Django. Отдельный `frontend/vercel.json` сохранён для запасного Render-профиля с корнем `frontend`; Services использует настройки из корневого файла.

Документация Vercel описывает доступ к GitHub organisation repos на Hobby неодинаково: проверяй фактический импорт в панели и используй личный fork, если он заблокирован. Основной командный репозиторий переносить не нужно; перед обновлением синхронизируй ветку fork.

## 3. Что происходит при сборке и запросах

Vercel Django preset устанавливает `requirements.txt` и собирает static. Runtime-зависимости перечислены только в `backend/requirements.txt`; настройки Ruff хранятся отдельно в `backend/ruff.toml`. Это важно для native Python builder: присутствующий `pyproject.toml` имеет приоритет над requirements, даже если содержит только настройки линтера. В первой сборке такой файл создал окружение без Django; после переноса Ruff в логе установки должен выбираться `requirements.txt`. Наш `vercel_build.py` сначала проверяет Production-окружение и обязательные настройки, затем один раз выполняет `migrate --noinput`. Миграции не запускаются при каждом запросе. Preview и сборка без ключей завершаются до обращения к рабочей БД. Для Preview впоследствии нужна отдельная база и отдельный профиль.

Все публичные маршруты направлены в Next.js. `/api` проходит через существующий bridge: он добавляет Django завершающий `/`, сохраняет cookies/CSRF и обращается к приватному backend. Публичного маршрута к `/admin`, Django static и legacy-интерфейсу в этом пилоте нет.

Bridge сохраняет служебный prefix binding URL и сам устанавливает `X-Forwarded-Host/Proto`. Django доверяет этим полям только при `SIPI_VERCEL_SERVICES=true`; список допустимых hosts и CSRF origins содержит точный основной адрес и выданные Vercel адреса этого проекта. Масок `*` и `.vercel.app` нет. Cookie защищены HTTPS.

ИИ обрабатывается внутри запроса, без бесконечного worker или локального Ollama. На одном Python-экземпляре одновременно выполняются не более двух запросов ИИ; остальные получают сообщение о занятости. Платформа может создавать несколько экземпляров, поэтому это не общая дневная квота. Общие лимиты Cloudflare всё равно действуют.

### Ограничения публичного API

Миграция `0017_ratelimitcounter` добавляет общие счётчики в БД: лимиты действуют между экземплярами приложения и не сбрасываются при перезапуске Python. Если счётчик недоступен, защищённый запрос возвращает `503`, а не выполняется без ограничения. Истёкшие записи очищаются небольшими порциями при активных запросах, без постоянного фонового процесса.

| Операция | Основной лимит | Дополнительные общие ограничения |
| --- | --- | --- |
| Вход | 10 попыток на IP + логин за 5 минут | 100 на IP и 1 000 суммарно за 5 минут |
| Регистрация | 5 запросов на email за час | 20 на IP и 100 суммарно за час |
| Запрос восстановления | 3 на email за 15 минут | 20 на IP и 1 000 суммарно за 15 минут |
| Подтверждение восстановления | 10 попыток на uid + IP за 15 минут | 100 на IP и 1 000 суммарно за 15 минут |

Дополнительно все API-потоки отправки писем — вход, регистрация, повторная отправка кода и восстановление — используют один бюджет: **10 попыток на email за час, 100 суммарно за час, 250 суммарно за 24 часа**. Это окна приложения, а не гарантия совпадения с календарным сбросом квоты почтового провайдера. Ошибка доставки не возвращает резерв; отклонённый из-за уже исчерпанного адресного лимита запрос не расходует общий бюджет. Ограничения самого провайдера продолжают действовать.

IP берётся из [платформенного заголовка Vercel](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for), проверяется в Next.js и передаётся через приватный binding. Переданные пользователем `X-Forwarded-For` и `X-Sipi-Client-IP` не используются как источник IP.

Эти изменения добавляют защиту API от перебора и массовой отправки. Прежняя политика сообщений о существовании аккаунта не меняется: восстановление отвечает одинаково для известной и неизвестной почты, а сообщения регистрации о занятом адресе сохраняются. Старые HTML auth views не переведены на этот limiter; в Services у `/legacy` нет публичного маршрута. При отдельной публикации legacy-интерфейса потребуется собственная проверка его ограничений.

## 4. Проверить живой стенд

По фактическому Production URL, отдельным тестовым аккаунтом:

1. Открывается интерфейс; `/api/livez` отвечает `{"status":"ok"}` без запроса к БД.
2. Регистрация, письмо с кодом и вход работают; неверный код отклоняется. Проверена и ссылка восстановления пароля.
3. Проект и задачи сохраняются после обновления страницы и нового развёртывания.
4. Помощник отвечает по разрешённым данным, создаёт проект/задачи, генерирует картинку; созданное сразу появляется в интерфейсе.
5. Отмена доступна во время ожидания ответа и показывает реальный результат сервера.
6. Посторонний не получает доступ к проекту; CSRF-запросы с чужого origin отклоняются.
7. URL binding с фактическими hostname/prefix работает в опубликованном проекте. Изображение скачивается как PNG и помещается в лимит ответа Vercel.

Эти пункты нельзя считать выполненными по одной production-сборке. Внутренний Host binding и маршрутизацию нужно проверить в самом Vercel-проекте.

## Квоты и обновление

Hobby предназначен для некоммерческого использования и имеет месячные лимиты. Python и Node Fluid Functions ограничены 300 секундами; прокси ждёт ИИ до 280 секунд. Локальные веса моделей, постоянные daemon-процессы и хранилище файлов в функции не используются.

Workers AI Free даёт 10 000 Neurons в день на текст и картинки. После исчерпания запросы возвращают ошибку без перехода на платный API. Brevo Free — до 300 писем в день; у SMTP выбранной почты действуют её собственные ограничения и правила отправки. Neon ограничивает размер базы и вычисления; не запускай keep-alive или постоянный опрос БД. Сгенерированные картинки занимают место в базе.

Бесплатные квоты провайдеров могут меняться. Перед созданием ресурсов проверь Free/Hobby в панели; тарифы автоматически не повышаются кодом. Сборка применяет миграции перед публикацией: изменения схемы должны быть совместимы с ещё работающей версией. Откат кода не отменяет миграции БД. Резервные копии остаются отдельной задачей.
