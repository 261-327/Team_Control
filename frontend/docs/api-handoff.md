# Django API для Сипи

Реализация: `backend/tasks/api.py`, сериализация: `backend/tasks/serializers.py`, общая валидация: `backend/tasks/forms.py`, маршруты: `backend/tasks/api_urls.py`. Все пути ниже имеют префикс `/api/` и завершающий `/` на стороне Django. Фронтенд использует серверный прокси `src/app/api/[...path]/route.ts`, который добавляет завершающий `/`, передаёт cookies, Origin и CSRF-заголовок. Host определяется адресом upstream, поэтому внешний Django получает свой домен. Серверный адрес настраивается через `DJANGO_API_URL` при запуске, включая standalone-образ.

Сессии — стандартные Django sessions, cookie `sessionid` с HttpOnly. `GET bootstrap/` выдаёт CSRF cookie. Любой изменяющий запрос требует `X-CSRFToken`; `csrf_exempt` не используется. Ответы API не кешируются. CSRF origins и разрешённые хосты настраиваются в окружении Django.

| GET           | `me/tasks/?page=1&pageSize=20`           | Постраничный список задач текущего пользователя               |
| GET           | `tasks/:id/`                             | Получение одной задачи                                        |
| GET           | `tasks/:id/comments/`                    | Получение комментариев задачи                                 |

`bootstrap` соответствует `Database` из `src/types/domain.ts`: строковые ID, ISO даты с часовым поясом, `sessionId`, `users`, `projects`, `memberships`, `tasks`, `events`, `comments`, `materials`, `invitations`, серверное `now`. Анонимный запрос возвращает пустые коллекции. `authChallenge` позволяет продолжить подтверждение после обновления страницы.

`PATCH projects/:id/settings/` принимает любое непустое подмножество полей `name` и `description`. Изменение доступно только пользователям с правом управления проектом и возвращает актуальный snapshot.

Изменяющие методы возвращают `{ snapshot, ... }`, при создании также `task`, `project` или `invitation`. Вход/выход возвращают сам snapshot. HTTP-адаптер публикует полученные данные после успешного сохранения. Ошибки имеют вид `{ error: { code, message } }` и соответствующий HTTP статус. Неудачный запрос оставляет форму открытой. Автоматических повторов изменяющих запросов нет. Раз в 30 секунд, при возвращении во вкладку и фокусе окна данные обновляются; websocket пока нет.

## Авторизация

Пароли проверяются Django validators, сохраняются штатными Django hashers. Шестизначный OTP хранится только в хешированном виде, действует 5 минут и допускает 5 попыток. Повторный запрос логина не сбрасывает лимит попыток. Код не возвращается в JSON: доставляется почтовым backend Django. При локальном console-backend интерфейс подсказывает посмотреть вывод терминала. SMTP-ошибка откатывает создание аккаунта. Отключённые администратором аккаунты через вход не активируются.

## Доступ и задачи

- Владелец проекта управляет задачами, колонками, материалами, приглашениями и участниками.
- Участник видит свой подтверждённый проект, комментирует, начинает назначенную ему задачу и отправляет её на проверку.
- Преподаватель имеет доступ к проектам с подтверждённым участием `access_role=teacher`; изменение задач запрещено.
- Координатор управляет только проектами с подтверждённым участием `access_role=coordinator`. Глобального доступа к чужим проектам нет. Тип аккаунта задаётся администратором через `account_type`; роли разработки относятся к Membership конкретного проекта.
- Поиск и вступление открыты авторизованным пользователям, как в исходном Django. Согласования заявок на вступление нет.
- Принять приглашение можно только из аккаунта с соответствующей почтой, до истечения срока и пока приглашение не обработано. Приглашения передаются ссылкой; почтовой рассылки для них нет.

### Изменение назначений проекта

- Владелец проекта или координатор с подтверждённым участием может изменять назначения руководителя и преподавателя.
- Руководителем может быть только активный пользователь с типом аккаунта `student`, преподавателем — активный пользователь с типом аккаунта `teacher`.
- Один пользователь не может одновременно быть руководителем и преподавателем проекта.
- Перед сохранением изменений требуется явное подтверждение в интерфейсе.
- Если новый руководитель является координатором этого проекта, требуется дополнительное подтверждение изменения его роли в рамках этого проекта. Роли в других проектах не меняются.
- Прежние руководитель и преподаватель остаются участниками проекта после смены назначения.

Основные статусы: `todo`, `in_progress`, `in_review`, `done`. Руководитель может исправить любой статус и вновь открыть готовую задачу. Исполнитель может пройти `todo → in_progress → in_review`. Из проверки в работу нужен комментарий о доработке. Приёмка записывает `accepted_at`, повторное открытие очищает его.

`move/` принимает `{ status, beforeTaskId?, reason?, resultUrl? }`. Отсутствие `beforeTaskId` означает конец колонки. API проверяет принадлежность целевой карточки, права и лимит, блокирует строку проекта в транзакции и сохраняет позиции вместе со статусом. Неудачный перенос не меняет карточку и историю. Лимит колонки — от 1 до 15 задач.

Миграции не удаляют существующие проекты, доски, колонки, задачи, участников и назначения. Известные названия старых этапов сопоставляются с основными статусами. Дополнительные колонки сохраняются отдельно с ID вида `column_123`; руководитель может переносить в них задачи, менять названия и лимиты. В новом интерфейсе колонки нескольких старых досок представлены на общей доске проекта. Добавление/удаление произвольных колонок остаётся в архивных шаблонах и админке. Старые задачи без срока показываются как «Без срока» и не экспортируются в календарь.

Задачи, созданные вручную, имеют одного исполнителя. Помощник может создать задачу без назначения. При чтении старых задач API дополнительно возвращает `assigneeIds`; изменение прочих полей сохраняет старые множественные назначения, пока в форме не выбран другой основной исполнитель.

## Помощник

Внешнего ИИ сейчас нет. `assistant/` получает запрос, проверяет проект и строит список ближайших сроков из реальных доступных задач. Остальные запросы получают честное сообщение о неподключённом агенте. Будущий провайдер подключается в этом обработчике, сохраняя серверную проверку доступа.

## Чтение задач и пагинация

Все перечисленные методы требуют авторизации через Django session cookie. Пользователь может получать задачи и комментарии только в проектах, к которым у него есть доступ.

### Список задач проекта

`GET /api/projects/:id/tasks/?page=1&pageSize=20`

Параметры:

- `page` — номер страницы, по умолчанию `1`.
- `pageSize` — число задач на странице, по умолчанию `20`, максимум `100`.

Ответ содержит `tasks` — массив задач в формате существующего `task_json`, и `pagination` с полями `page`, `pageSize`, `totalTasks`, `totalPages`.

### Личные задачи

`GET /api/me/tasks/?page=1&pageSize=20`

Возвращает задачи, назначенные текущему пользователю в доступных ему проектах. Поддерживает те же параметры пагинации.

### Одна задача

`GET /api/tasks/:id/`

Возвращает объект `task` в формате `task_json`. Для чтения достаточно доступа к проекту. Изменение и удаление задачи по-прежнему требуют прав управления проектом.

### Комментарии задачи

`GET /api/tasks/:id/comments/`

Возвращает массив `comments`. Каждый элемент содержит `id`, `taskId`, `userId`, `text`, `createdAt`. Комментарии отсортированы от старых к новым. Существующий `POST /api/tasks/:id/comments/` продолжает создавать комментарии.

### Пагинация и ошибки

Некорректные параметры пагинации и номер несуществующей страницы возвращают HTTP 400. Если задач нет, сервер возвращает пустой массив `tasks` и `totalTasks: 0`, `totalPages: 0`.

Ошибки API используют общий формат `{ "error": { "code": "...", "message": "..." } }`. Для анонимных запросов требуется авторизация; для недоступного проекта или задачи возвращается ошибка 404.

## Восстановление пароля

- `POST auth/password-reset/` принимает `{"email":"user@example.com"}`. Для существующей активной учётной записи с подтверждённой почтой отправляет ссылку; для неизвестной почты возвращает такой же успешный ответ. Письмо отправляется настроенным Django email backend (локально — console/file, на сервере — SMTP).
- Ссылка содержит `uid` и токен Django `PasswordResetTokenGenerator`. Токен не хранится в базе и не возвращается в JSON; он связан с состоянием пользователя, становится недействительным после смены пароля и действует 30 минут.
- `POST auth/password-reset/confirm/` принимает `{"uid":"…","token":"…","password":"…","passwordConfirm":"…"}`. Сервер повторно проверяет токен под блокировкой записи, запускает штатные Django password validators, меняет пароль и удаляет сохранённые Django-сессии пользователя. Отключённые администратором аккаунты не активируются.
- Запросы восстановления ограничиваются по IP + нормализованной почте; проверки токена — по IP + UID. Все изменяющие запросы по-прежнему требуют CSRF. После сброса пользователь должен войти с новым паролем и пройти обычный OTP.

## Дополнения по команде и обсуждению

`PATCH /api/projects/:projectId/members/:userId/role/` принимает тот же объект профессии, что самостоятельная смена роли. Менять чужую профессию могут владелец и подтверждённый координатор проекта. Права управления, владелец и подтверждение членства сохраняются. Автор и описание изменения записываются в ProjectEvent. Ответ содержит snapshot.

В `GET /api/colleagues/` для подтверждённых коллег добавлено поле `pendingProjectIds`. Оно содержит проекты, которыми текущий пользователь может управлять и куда коллеге уже отправлено действующее приглашение. Адрес коллеги в ответе не раскрывается. `POST /api/colleagues/:connectionId/invite/` с projectId создаёт приглашение, которое получатель принимает отдельно.

Новый комментарий создаёт уведомления владельцу проекта, автору задачи, исполнителям и предыдущим авторам обсуждения с текущим подтверждённым доступом. Автор нового комментария исключён, получатели не дублируются. Исторические комментарии при миграции считаются прочитанными.

`GET /api/notifications/` возвращает для новых комментариев kind=comment, projectId и taskId. Колокольчик показывает одну ссылку на обсуждение каждой задачи. Обновление колокольчика происходит раз в 15 секунд, snapshot со счётчиками задач обновляется раз в 30 секунд и после собственных изменений.

В задачах bootstrap/snapshot добавлено unreadCommentCount для текущего пользователя. `POST /api/tasks/:id/comments/read/` принимает `{"lastCommentId":"123"}` и отмечает прочитанными только уведомления этого пользователя до указанного комментария включительно. Более новые сообщения остаются непрочитанными. Web вызывает метод, когда конец обсуждения виден на экране. Запрос требует сессию, CSRF и действующий доступ к проекту. Ответ содержит snapshot. После исключения из проекта его уведомления удаляются, чтение и запись запрещены.

Проекты используют вступление по приглашению во всех окружениях. Каталог ищет только доступные текущему пользователю проекты. Самостоятельный join возвращает 403, включая DEBUG и старую настройку PROJECT_SELF_JOIN_ENABLED. Существующие подтверждённые членства сохраняются.

При переходе задачи в todo прежний resultUrl переносится в событие истории, актуальная ссылка и даты сдачи/приёмки очищаются. При возврате на доработку в in_progress ссылка также переносится в историю и очищается в актуальном результате. Перемещение внутри того же статуса не меняет результат.
