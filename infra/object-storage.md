# Постоянное приватное хранилище материалов

## Архитектура

Production в Vercel Services использует S3-совместимое объектное хранилище для байтов файлов. Django сохраняет в PostgreSQL метаданные и ключ объекта. Bucket закрытый; приложение не публикует объектные URL. Каждый download проходит через Django и повторно проверяет членство в проекте.

Локальная разработка и Docker Compose по умолчанию используют FileSystemStorage. В serverless-профиле без object storage endpoints файлов возвращают 503, а не записывают данные во временную файловую систему.

## Переменные окружения

- `PROJECT_MEDIA_STORAGE=filesystem|s3`
- `OBJECT_STORAGE_ENDPOINT_URL` — HTTPS S3 endpoint, например `https://<account-id>.r2.cloudflarestorage.com`
- `OBJECT_STORAGE_BUCKET` — имя приватного bucket
- `OBJECT_STORAGE_ACCESS_KEY_ID` — bucket-scoped access key
- `OBJECT_STORAGE_SECRET_ACCESS_KEY` — секретный ключ
- `OBJECT_STORAGE_REGION=auto` для Cloudflare R2

Секреты добавляются только в защищённые настройки окружения backend. Не добавляй их в Git, issue, PR, frontend или логи. Для R2 используй отдельные credentials с минимальными правами на один bucket. Публичный доступ, custom domain и `r2.dev` не включать.

## Перенос локальных файлов

Если исходные файлы существуют в `MEDIA_ROOT`, включи S3 backend и выполни из backend-каталога:

```sh
python manage.py migrate_material_files_to_object_storage --dry-run
python manage.py migrate_material_files_to_object_storage
```

Команда сверяет размер и SHA-256, проверяет уже существующий объект, обновляет ключ в БД только после успешной проверки и не удаляет локальный оригинал. Запускать её нужно в окружении, где доступен исходный каталог/volume. Если прежняя serverless-функция уже потеряла временные файлы, нужен внешний backup или исходники от пользователя — восстановить их из новой функции нельзя.

## Проверка

1. Убедись, что bucket приватный и credentials ограничены одним bucket.
2. Проверь, что Django стартует только при полном наборе параметров для `PROJECT_MEDIA_STORAGE=s3`.
3. Загрузить тестовый PDF/PNG/JPEG.
4. Проверить объект в приватном bucket и отсутствие публичного доступа к нему.
5. Скачать через защищённый endpoint участником проекта; проверить 404 для постороннего/исключённого пользователя.
6. Удалить материал и проверить удаление объекта.
7. Повторить скачивание после redeploy и с нового экземпляра backend.
8. Выполнить тестовое восстановление БД и объектов в отдельной среде.

## Резервные копии

R2/object storage не заменяет backup. В рамках #16 нужно резервировать PostgreSQL и объекты в согласованном временном окне, хранить копию отдельно с ограниченным доступом и фактически проверить восстановление в изолированную среду. Не удалять исходную копию до проверки новой.
