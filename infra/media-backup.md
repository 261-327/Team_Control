# Резервное копирование файлов материалов проекта

Загруженные PDF/PNG/JPEG лежат в приватном Docker volume `media_data`, смонтированном в backend как `/app/media`. Папка не раздаётся nginx как статический каталог: скачивание проходит через Django и проверяет актуальное членство в проекте.

## Создание копии

Команды выполняются на сервере из корня репозитория. Каталог резервных копий должен находиться вне Git и иметь ограниченные права доступа.

```sh
mkdir -p /var/backups/team-control
chmod 700 /var/backups/team-control
stamp=$(date -u +%Y%m%dT%H%M%SZ)
docker compose -f compose.server.yaml exec -T backend tar -czf - -C /app/media . > "/var/backups/team-control/media-$stamp.tar.gz"
test -s "/var/backups/team-control/media-$stamp.tar.gz"
sha256sum "/var/backups/team-control/media-$stamp.tar.gz" > "/var/backups/team-control/media-$stamp.tar.gz.sha256"
```

Метаданные материалов находятся в PostgreSQL. Для согласованной точки восстановления делайте дамп БД в том же окне обслуживания и сохраняйте оба файла под одним timestamp. Не удаляйте старые копии, пока не проверена новая. Дамп и архив media не загружать в GitHub.

## Проверка архива без изменения рабочего хранилища

```sh
tar -tzf /var/backups/team-control/media-<timestamp>.tar.gz
sha256sum -c /var/backups/team-control/media-<timestamp>.tar.gz.sha256
```

## Восстановление

Восстанавливать нужно только в отдельный тестовый экземпляр приложения и отдельную тестовую базу, не поверх рабочей базы/volume. Сначала разверните соответствующий дамп PostgreSQL в пустую тестовую БД, затем распакуйте media-архив в отдельный тестовый каталог/volume, подключённый к тестовому backend как `MEDIA_ROOT`. После восстановления проверьте через Django shell, что у записей `Material(kind="file")` существует файл по `file.name`, а участник проекта может скачать его через защищённый endpoint. Также проверьте, что пользователь без членства получает 404.

**Важно:** эта инструкция добавляет media к плану резервирования, но сама по себе не подтверждает успешное восстановление. До использования реальных данных ответственный за #16 должен выполнить пробное восстановление БД и media в изолированной среде, зафиксировать дату, результат и время восстановления, а также настроить закрытое внешнее место хранения и расписание копирования.
