# Участие пользователей в проектах

## Связи

`WorkspaceUser 1 — N Membership N — 1 Project`.

`Project.members` — ManyToMany через явную модель `Membership`, а не отдельную неявную таблицу.
Один аккаунт может иметь несколько строк Membership для разных проектов. Поля `role`,
`developer_specialization`, `custom_role`, `is_confirmed`, `joined_at` относятся к конкретной строке участия.
В WorkspaceUser этих полей ролей больше нет. Например, один пользователь — backend-разработчик
в проекте A и дизайнер в проекте B; изменение второй роли не затрагивает первую.

Уникальное ограничение PostgreSQL `unique_user_project_membership(user_id, project_id)`
запрещает дубли даже при записи вне формы. Вступление использует транзакцию и блокировку проекта.
Повторная отправка формы не создаёт вторую строку и не меняет уже подтверждённую роль.

Роли: разработчик, дизайнер, аналитик, безопасник, тестировщик, другое.
Для разработчика обязательно направление backend/frontend/iOS/Android; для «Другое» — свой текст.
Профессия выбирается при создании проекта или вступлении, а не при регистрации аккаунта.

`Project.owner` остаётся FK, определяющим владельца и его административные права:
это не профессия и не глобальная роль User. Изменение профессии Membership не повышает права.
Владельцу доступны настройки статусов, удаление проекта и участников; участникам — работа с задачами.

Исполнители задач выбираются из активных подтверждённых участников соответствующего проекта
и его владельца. До личного вступления/открытия проекта legacy-участие не даёт права назначать
пользователя. Выход/удаление удаляет Membership и назначения в этом проекте,
не меняя аккаунт, авторство задач и другие команды.

## Миграции

Ветка также содержит ранее не опубликованные экраны проектов, задач и статусов и необходимые
миграции 0004–0008. `0009_explicit_membership` создаёт модель Membership и переносит объединение
старых members, confirmed_members и владельца с дедупликацией; роль и уточнения копируются
из прежнего профиля в каждую существующую команду пользователя. Подтверждение сохраняется;
владелец подтверждён. Затем удаляются старые две M2M-таблицы и глобальные поля роли.
Для старых строк joined_at — время переноса: историческая дата вступления раньше не хранилась.

Перед изменением рабочей базы сделайте резервную копию PostgreSQL. Применение:

```sh
python manage.py migrate
```

0004 останавливается, если старые аккаунты имеют одинаковую непустую почту; такие адреса
нужно исправить до повторного migrate. Миграции не удаляют аккаунты и задачи.
При откате 0009 старые связи восстанавливаются, но разные роли нескольких проектов
невозможно без потерь свести к одному глобальному полю — для полного отката нужна резервная копия.

## Проверка через админку

1. Создайте два проекта и вступите одним аккаунтом в оба с разными ролями.
2. `/admin/tasks/project/`: откройте каждый проект; inline показывает пользователей,
   роль, направление, своё название и подтверждение отдельно для каждой команды.
3. `/admin/tasks/membership/`: фильтры по проекту, роли и подтверждению.
4. `/admin/tasks/workspaceuser/`: карточка пользователя содержит его участия в нескольких проектах.
5. Попытка добавить ту же пару user/project повторно отклоняется формой и ограничением БД.

## Проверки

```sh
python manage.py check --settings=config.test_settings
python manage.py makemigrations --check --dry-run --settings=config.test_settings
python manage.py test tasks --settings=config.test_settings
```

По умолчанию test_settings использует SQLite в памяти и почту в памяти.
`TEST_POSTGRES=1` переключает проверки на PostgreSQL через DB_NAME, DB_USER, DB_PASSWORD,
DB_HOST, DB_PORT. GitHub Actions запускает suite и миграционные проверки на PostgreSQL 15.
Тестируются два проекта/разные роли, запрет дублей, формы профессий, миграция старых данных,
страницы admin для обеих команд, доступ, назначение только участникам и сохранность остальных функций.
