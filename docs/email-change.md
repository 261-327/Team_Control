# Безопасное изменение email — #100

База: main fdcb55e, версия сайта 0.2.0. Ветка feat/100-secure-email-change.

В профиле кнопка «Изменить почту». Требуются текущий пароль и код, доставленный
на новый адрес. Старый email остаётся действующим до успешного подтверждения.
Шестизначный код хранится только в хеше, действует 5 минут, допускает 5 попыток;
повторный запрос с паролем разрешён через 60 секунд и заменяет предыдущий challenge.
Пароль после запроса удаляется из состояния формы, code не выдаётся в API.

## API

Оба POST требуют session cookie, CSRF и Content-Type application/json.

POST /api/profile/email-change/

```json
{"email":"new@example.test","password":"<текущий пароль владельца>"}
```

Ответ 200: message, expiresAt, resendAt (ISO 8601). Ответ не содержит адреса,
пароля, кода и внутренних ошибок почтового сервиса. Для занятого/собственного адреса
одинаковая нейтральная ошибка без сведений об аккаунте. Публичного метода проверки
занятости нет. Ошибки: 400 validation, 401 unauthenticated, 403 csrf,
429 rate_limited, 503 unavailable. Не публиковать тела реальных запросов.

POST /api/profile/email-change/confirm/ принимает объект с полем code (строка из
письма). 200: message и анонимный snapshot после выхода. 400 invalid_code_format
для формата; validation для неверного/истёкшего/уже использованного подтверждения.
Повтор после выхода — 401. Для отправки/подтверждения есть общие HMAC-лимиты по
пользователю/IP и бюджет почты. SMTP-ошибка откатывает новый challenge.

## Согласованность

Email нормализуется trim/lower; сохраняется только после проверки текущего пароля,
кода и привязки к сессии, предыдущему email и хешу состояния пароля. Пароль/почта,
изменённые параллельно, делают challenge недействительным. Строка пользователя
блокируется select_for_update, уникальность email дополнительно защищена БД;
IntegrityError при одновременном захвате адреса возвращает нейтральную ошибку.
Один пользователь имеет только один challenge. После успеха challenge удаляется,
старый OTP входа очищается, все Django-сессии завершаются. Ранее выданные ссылки
сброса пароля перестают действовать по стандартному Django token generator.

Вход и восстановление используют новую каноническую почту. Приглашения на старый
адрес не переписываются: они адресованы владельцу именно того почтового ящика.
Существующее участие в проектах связано с user ID и сохраняется. Приглашения на
новую почту становятся доступны этому аккаунту после смены; username не меняется.

## Проверки и запуск

Миграция: 0024_email_change_challenge. Применить python manage.py migrate.
Миграция из независимой ветки #103 имеет тот же номер с другим именем; если обе
попадут в main, потребуется стандартная merge-миграция Django.

python manage.py test tasks.test_email_change tasks.test_api --settings=config.test_settings

51 тест прошёл на отдельной SQLite базе. Проверены пароль, формат/занятость,
старый адрес до подтверждения, срок, попытки, повтор, другая сессия, смена пароля,
повторная отправка, SMTP rollback, занятый после запроса адрес, CSRF, отзыв сессий,
вход и восстановление по новому адресу, недействительность старого reset token,
сохранение приглашений. Реальная многопоточная гонка PostgreSQL отдельно не
запускалась; проверен конфликт состояния и присутствие защиты уникальностью БД.

Playwright e2e/email-change.spec.ts прошёл с mock API: профиль → пароль/новый адрес →
код → выход. Серверные тесты используют настоящий Django API с locmem почтой,
