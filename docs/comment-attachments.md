# Вложение комментария — #113

Версия 0.2.0, ветка feat/113-comment-attachments. Изменения локальные.

В форме обсуждения можно выбрать один файл, увидеть имя/размер, открыть выбранное
содержимое или убрать его до отправки. Для DOCX просмотр зависит от приложения
компьютера. При отправке требуется непустой текст комментария. Ошибка сохраняет
текст и выбранный файл. После успеха файл показан непосредственно в сообщении,
а не в общем списке материалов задачи.

Используются validate_file, download_file, FileField с текущим private storage и
существующий delete_private_file. Форматы и лимит 3 МБ совпадают с файлами задач:
PDF/DOCX/TXT/MD/CSV/PNG/JPEG; проверки содержимого те же. Это не отдельный антивирус.
Серверный флаг PROJECT_FILE_UPLOADS_ENABLED должен быть включён для отправки.

## API

POST /api/tasks/1/comments/files/ — multipart/form-data: text, file, requestId (UUID).
Требуются session, CSRF и текущее право просмотра проекта. requestId обязателен:
клиент сохраняет его при повторе неизменённой отправки. Смена текста/файла создаёт
новый ID. Пример полей: text=«Пример сообщения», file=demo.txt,
requestId=11111111-1111-4111-8111-111111111111 (вымышленные данные).

Ответ 200: commentId и snapshot. В комментариях snapshot и GET comments добавлен
attachments: массив (пока 0 или 1) с id, fileName, fileSize, contentType, downloadUrl.
Например: {"id":"1","fileName":"demo.txt","fileSize":4,"contentType":"text/plain",
"downloadUrl":"/api/comment-attachments/1/download/"}.
Прежний JSON POST comments/ без файлов не меняется.

GET /api/comment-attachments/1/download/ проверяет актуальный доступ к проекту
через комментарий → задачу. Возвращает private/no-store, nosniff и attachment,
не публичный URL объекта хранилища. После исключения пользователя — 404.

Повтор того же requestId с тем же автором, задачей и fingerprint текста/файла
возвращает исходный commentId без новой записи/уведомлений/файла. Изменённое тело
с тем же ключом — 409; чужой автор/задача — 404. Проект блокируется в транзакции,
requestId дополнительно уникален в БД. Удалённые сообщения не служат вечными
квитанциями: повтор старого запроса после удаления сообщения не поддерживается.
Клиент не должен повторять уже удалённое сообщение.

Ошибка до сохранения не пишет файл; ошибка после записи файла откатывает БД и
удаляет новый объект. Уведомления создаются общей notify_comment, как у обычного
сообщения. Удаление комментария/задачи/проекта каскадно удаляет CommentAttachment;
байты очищаются существующим storage-механизмом после commit (DatabaseStorage
в транзакции). Сбой внешнего storage delete требует операционного контроля так же,
как у существующих материалов. Прямые файлы материалов/задачи не затрагиваются.

## Проверки

50 Django-тестов (test_comment_files + test_api) прошли на отдельной SQLite БД.
Проверены повтор без дублей, конфликт содержимого, чужой requestId, сериализация,
скачивание, потеря участия, анонимный доступ, CSRF, неверные форматы/сигнатура/размер,
пустой текст, rollback и отсутствие потерянного файла, каскадная очистка.
Реальное S3/R2 окружение и многопоточная PostgreSQL гонка отдельно не запускались.

Браузерный e2e/comment-files.spec.ts прошёл с mock API: выбор/убрать/повторный выбор,
просмотр кнопки, отправка, привязка к сообщению и reload. Данные вымышленные.
